01 The problem

Why basic OCR fails on business documents

Traditional text recognition dumps words into a flat string. It cannot tell whether "$500" is a subtotal, a discount, or the final invoice balance.

Plain OCR reads words but loses structure

Plain text readers strip out 2D coordinates. Column relationships collapse into an unordered sequence of words.

Layout tells you which number is the total

The total usually sits below the subtotal, to the right of line items. Position on the page is as informative as the text itself.

We combine text, position and image

Digital PDFs read coordinates directly from vector streams. Scanned receipts pass through a vision transformer without an OCR pre-step.

02 Architecture & Pipeline

A 3-stage pipeline with deterministic post-processing

Extracts documents across modalities, normalizes dates and currencies, reconstructs hierarchical parent-child relationships via X-axis coordinate offsets (Δx0), and verifies arithmetic integrity.

Stage 01

Format & Modality Router

Inspects the document's vector text layer. If text density exceeds 20 words, it routes to the microsecond 2D geometric layout parser. Scans and flattened camera images route to the Donut vision transformer.

Stage 02

2D Spatial & Visual Extraction

PyMuPDF captures precise word coordinates [x0, y0, x1, y1], clusters words into lines by Y-center distance, and stitches multi-page tables across repeated headers. Donut uses Swin Transformer cross-attention directly from raw pixels.

Stage 03

Structured Post-Processor

Normalizes ISO dates, cleans currency strings, reconstructs nested parent-child modifier hierarchies via X-axis indentation (Δx0 > 12px) and prefix tokens, and runs an automated Mathematical Reconciliation Check (sum(items) + tax == total).

When each engine and pipeline stage is used
Pipeline Stage Mechanism & Component Latency Profile Core Responsibilities & Guarantees
Stage 1: Router Word Density Classifier <0.001s Routes text-layer PDFs (>20 words) to 2D layout parser; routes scans/photos to Donut VLM.
Stage 2A: 2D Layout PyMuPDF Spatial Extractor <0.03s Exact coordinate line clustering, column range bounding, multi-page table stitching.
Stage 2B: Vision VLM Donut Swin Transformer 2.7 – 4.5s Zero-OCR pixel parsing for crumpled receipts, angled camera photos, and flat scans.
Stage 3: Post-Processor Deterministic Schema Engine <0.002s Reconstructs nested modifiers via X-indent (Δx0), normalizes dates, verifies arithmetic integrity.

05 Architectural trade-offs

Donut vs. LayoutLMv3

Why our system implements a dual-engine architecture instead of relying solely on an OCR-dependent multimodal model.

Comparison between Donut and LayoutLMv3
Dimension Donut (Vision-Language Model) LayoutLMv3 (Multimodal OCR)
How it reads the page Reads raw image pixels directly via Swin Transformer encoder. Requires external OCR to extract words and coordinates prior to inference.
Needs OCR Zero OCR binaries. Self-contained model weights. Strict reliance on Tesseract or system OCR binaries.
Strengths Immune to OCR word-splitting errors; fast single-pass inference. Strong grounding in coordinate positions for dense forms.
Weaknesses Autoregressive decoder can repeat or hallucinate tokens on unfamiliar layouts. Fails completely when the OCR pre-step misses or misreads words.
Best for Camera photos, crumpled receipts, and flattened scans. Clean document scans with standard, pre-installed OCR pipelines.

Architectural takeaway: Donut avoids fragile OCR installation issues in hackathon and edge environments. However, because CORD weights specialize in Indonesian receipts, digital business invoices are best handled by PyMuPDF's exact coordinate geometric clustering, achieving sub-30ms execution.

07 Limitations and roadmap

Current boundaries and upcoming engineering

Clear documentation of technical constraints and planned improvements.

Receipt-trained weights

Donut uses CORD-v2 weights trained on store receipts. Complex multi-column corporate invoices are handled by the layout engine.

Multi-page scans

Digital multi-page PDF tables stitch cleanly across page boundaries. Extending autoregressive visual attention across multi-page photo scans remains in development.

Hierarchical nested modifiers

X-axis indentation offsets (Δx0 > 12px) and prefix token classification (+, -, *, Discount:) are now supported for vector digital layouts. Extending visual nested attention across dense unaligned photo scans is the next milestone.

Handwriting

Faded handwriting and manual cursive additions are outside current model scope.

Next engineering steps

  • Fine-tune Donut decoder on DocVQA and complex enterprise balance-sheet datasets.
  • Extend hierarchical nested modifier attention from vector 2D layouts into dense unaligned vision transformer tokens.
  • Add WebAssembly packaging to execute the coordinate layout parser client-side.
08 Run it locally

Setup and local execution

Steps to run the local FastAPI backend, evaluation runner, and test suite.

1. Clone repository and initialize environment 
git clone https://github.com/anything14907-byte/Foss.git
cd Foss
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
2. Start local FastAPI server (http://localhost:8000) 
uvicorn backend.app:app --host 127.0.0.1 --port 8000
3. Test extraction with cURL 
curl -X POST "http://localhost:8000/parse-document?mode=auto"   -F "file=@data/eval/invoice_consulting_services.pdf"
4. Run evaluation benchmark and tests 
python evaluate.py
pytest tests/
